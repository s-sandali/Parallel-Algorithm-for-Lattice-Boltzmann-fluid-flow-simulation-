SE3082 – Parallel Computing – Assignment 03

The Lattice Boltzmann Method

A mesoscopic approach to computational fluid dynamics — how it works, step by step, and how we parallelise it across OpenMP, MPI, and CUDA.

The Problem

Two ways to simulate fluid flow

Traditional CFD solves the Navier-Stokes equations directly — partial differential equations that describe how velocity, pressure, and density change over time. This is mathematically elegant but computationally expensive: you need to solve coupled, nonlinear PDEs, often requiring implicit solvers and iterative pressure correction.

The Lattice Boltzmann Method takes a completely different approach. Instead of solving macroscopic equations, it simulates the behaviour of fictitious particle populations bouncing around on a discrete grid. Density and velocity emerge naturally as statistical averages. The Chapman-Enskog expansion proves that this recovers the incompressible Navier-Stokes equations in the limit.

Traditional CFD

Navier-Stokes (macroscopic)

  • Solve coupled PDEs for velocity and pressure
  • Needs pressure-velocity coupling (SIMPLE, etc.)
  • Implicit solvers, matrix inversions
  • Complex boundary handling
  • Hard to parallelise (global pressure solve)
vs
Lattice Boltzmann (mesoscopic)

D2Q9-BGK

  • Track 9 particle distributions per cell
  • No pressure equation needed
  • Explicit time stepping, no matrix solves
  • Simple bounce-back for solid walls
  • Naturally parallel (local operations)
The Model

D2Q9 — 2 dimensions, 9 velocities

Each cell on the 600×200 grid holds 9 distribution functions (f₀ through f₈). Each one represents how much fluid is moving in that direction. The weights reflect how likely each direction is at thermodynamic equilibrium.

The D2Q9 velocity model. Cardinal directions get weight 1/9, diagonals 1/36, rest 4/9.
The Algorithm

What happens each timestep

The simulation runs this 6-step cycle 10,000 times. Each step operates on the same 600×200 grid of cells. The heavy computation is in steps 1–3; steps 4–5 are cheap boundary fixes; step 6 is just a pointer swap.

1

Compute density and velocity

What does this cell's collection of particles mean physically?

Sum all 9 distributions to get density (ρ). Weight each by its direction to get momentum, then divide by ρ to get velocity (ux, uy). If East=20 and West=5, more fluid is heading right, so ux is positive.

// For each cell (x, y): ρ = f₀ + f₁ + f₂ + ... + f₈ ux = (f₁ - f₃ + f₅ - f₇ + f₈ - f₆) / ρ uy = (f₂ - f₄ + f₅ - f₇ + f₆ - f₈) / ρ

⬡ Purely local — each cell reads only its own data. No neighbours needed.

2

Collision (BGK relaxation)

Particles inside the cell bump into each other and try to reach equilibrium.

Each distribution is nudged toward the equilibrium value (what thermodynamics says it "should" be at this density and velocity). The parameter τ = 0.6 controls how fast this happens. Lower τ means lower viscosity means more turbulent flow.

// BGK operator — relax toward equilibrium f[i] = f[i] − (1/τ) × (f[i] − feq[i]) // where f_eq depends on current ρ, u_x, u_y: feq[i] = w[i] × ρ × (1 + 3(e·u) + 4.5(e·u)² − 1.5|u|²)

⬡ Still purely local — nothing moves to neighbours yet.

3

Streaming (particles travel)

Each distribution hops one cell in its direction.

This is where fluid information actually moves between cells. The code uses pull-style: instead of pushing particles out, each cell asks "who was upstream?" and pulls from there. The result goes into a separate buffer (fnew) so reads and writes don't collide.

Pull-style streaming: Cell B reads from Cell A. Each cell only writes to itself.

If the upstream cell is solid (part of the cylinder), the particle bounces back instead — its direction gets reversed. This creates a no-slip wall where velocity equals zero at the surface.

⬡ Reads 8 neighbours — this is the stencil step. The key target for parallelisation.

4

Inlet boundary (Zou-He)

Force velocity = 0.1 at the left wall.

At x = 0, the simulation prescribes ux = U_INLET and analytically computes the three unknown incoming distributions (f₁, f₅, f₈). Without this, the fluid would eventually stop flowing.

⬡ Only touches one column (x = 0). Very cheap.

5

Outlet boundary (zero-gradient)

Let fluid flow out smoothly at the right wall.

At x = NX−1, all 9 distributions are copied from the second-to-last column. This prevents reflections at the boundary.

⬡ Only touches one column (x = NX−1). Also very cheap.

6

Swap buffers

fnew becomes the current state for the next timestep.

Just swap two pointers. No data is copied — only two pointer values trade places. Then the cycle repeats.

⬡ One pointer swap. Zero cost.

↓
2. Collision — relax toward equilibrium
↓
3. Stream — particles move to neighbours
↓
4 & 5. Fix inlet and outlet boundaries

Parallelisation

Three ways to run it faster

Steps 1 and 2 are embarrassingly parallel — every cell is independent, no data conflicts. Step 3 reads neighbours (a stencil) but each cell writes only to its own location. This structure maps cleanly to all three parallel paradigms.

🧵 Shared Memory

OpenMP

Add #pragma omp parallel for collapse(2) to the 3 heavy loops. All threads share the same arrays. 7 lines added to serial code. Peak: 57.6 MLUPS at 8 threads (2.6× speedup).

📨 Distributed Memory

MPI

Split the 600 columns across processes. Each gets a strip + 2 ghost columns. Exchange boundary data with MPI_Sendrecv after collision. Peak: 44.5 MLUPS at 4 procs (1.4× speedup).

⚡ GPU

CUDA

One thread per cell. 2D grid of 16×16 blocks. 5 kernels per timestep. Data stays on GPU; only copied back every 100 steps for output. Peak: 70.8 MLUPS (3.2× speedup).

OpenMP — what changes

The serial loops over (x, y) get a single pragma. collapse(2) flattens 600×200 into 120,000 iterations. Static schedule because every cell does the same work. No reductions, no critical sections — each cell writes to its own spot.

#pragma omp parallel for collapse(2) schedule(static) for (int x = 0; x < NX; x++) for (int y = 0; y < NY; y++) { // compute rho, ux, uy from f[x][y] // each thread writes ONLY to its own (x,y) }

MPI — domain decomposition + halo exchange

The grid is split along x. With 4 processes, each gets 150 columns plus 2 ghost columns for neighbour data. After collision, one MPI_Sendrecv sends the rightmost column to the right neighbour and receives the left ghost from the left neighbour. A second call does the reverse.

1D decomposition with 4 ranks. Red arrows show ghost column exchanges after collision.

CUDA — one thread per cell, five kernels per timestep

The 600×200 grid maps to a 2D CUDA grid. Each thread computes one cell using blockIdx and threadIdx. Five separate kernels run per timestep because threads in different blocks cannot synchronise within a single kernel. Launching a new kernel is the only global barrier available.

dim3 block(16, 16); // 256 threads per block dim3 grid((600+15)/16, (200+15)/16); // enough blocks to cover grid for (t = 1; t <= 10000; t++) { macroscopic_kernel<<>>(d_f, d_rho, d_ux, d_uy, ...); collision_kernel<<>>(d_f, d_rho, d_ux, d_uy, ...); streaming_kernel<<>>(d_f, d_fnew, ...); inlet_kernel<<>>(d_fnew, ...); outlet_kernel<<>>(d_fnew, ...); swap(d_f, d_fnew); // pointer swap, no data copy }
